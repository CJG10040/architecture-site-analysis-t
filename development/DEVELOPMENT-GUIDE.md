# 대지해석 에이전트 개발 진행 지침서

## 1. 목적

이 프로젝트는 데이터를 많이 보여주는 GIS 대시보드나 일반 챗봇이 아니라, 자료와 현장 관찰을 건축적 사고로 전환하는 대지해석 에이전트를 만든다.

```text
자료 수집
→ 데이터 품질·출처 확인
→ 사실
→ 공간·시간·속성 관계
→ 분야별 핵심 이슈·키워드
→ 현장 검증
→ 설계 질문
→ 복수 설계 가설
→ 분야 간 종합
```

## 2. 작업 순서 원칙

1. 전체 작업의 큰 틀은 `development/TODO.md`에서 관리한다.
2. 큰 TODO 항목을 시작하기 전에는 반드시 `development/tasks/` 아래에 해당 작업의 세부 TODO를 만든다.
3. 세부 TODO에는 작업 범위, 사용 자료, 수정 파일, 완료 조건, 검증 방법을 포함한다.
4. 세부 TODO를 작성·확인하기 전에는 구현·대량 자료 추가·다음 단계 진입을 하지 않는다.
5. 한 항목은 구현만으로 완료하지 않는다. 테스트, 실제 응답 또는 결과 검증까지 끝난 뒤 `[x]`로 체크한다.
6. 진행 중인 항목과 차단된 항목은 TODO에 기록하고 숨기지 않는다.
7. 사용자가 확인해야 하는 결정은 구현 전에 별도로 확인받는다.

## 3. 세부 TODO 작성 규칙

큰 항목을 시작할 때 다음 형식의 파일을 만든다.

```text
development/tasks/B-01-building-data-audit.md
```

세부 TODO에는 다음을 작성한다.

```markdown
# B-01 작업

## 목적

## 이번 작업에 포함하는 것

## 이번 작업에서 제외하는 것

## 사용할 자료·출처

## 수정 예정 파일

## 세부 TODO

- [ ] ...

## 완료 조건

## 검증 방법

## 사용자 확인이 필요한 결정
```

작업 중 요구사항이 늘어나면 세부 TODO에 추가하고, 범위를 크게 바꾸면 사용자 확인을 다시 받는다.

## 4. 조사 분야 진행 원칙

한 번에 여러 조사 분야를 섞지 않는다.

```text
주변 건축물 조사 완료
→ 사용자 검토
→ 다음 조사 분야 계획
→ 세부 TODO 작성
→ 다음 분야 구현
```

건축물 분야 안에서도 다음 순서로 진행한다.

```text
원본 자료 조사
→ 건축물 ID·필드 결합
→ 건축물 마스터 정규화
→ 거시·중간·대지·미시 분석
→ 지도·표·도면 표현
→ 건축물 전용 AI 분석
→ 사용자·QGIS 결과 검토
```

## 5. 자료 보존과 데이터 계층

원본과 분석 결과를 섞지 않는다.

```text
raw data
: API·SHP·GeoJSON·CSV의 원본 응답과 파일

normalized data
: 자료원별 필드를 통일한 분석용 데이터

field observation
: 사용자가 현장에서 확인한 사진·메모·시각·위치

analysis result
: 계산된 관계·이슈·키워드·설계 질문·가설
```

원본 자료는 최대한 보존하되, AI에는 조사 범위와 분석 단계에 맞는 정보만 보낸다.

## 6. 범위별 정보량 원칙

```text
거시 500m~1km
: 전체 건축물의 geometry, footprint 면적, 분포·밀도·집계 중심

중간 300m
: 전체 건축물의 기본 속성, 용도·층수·시기·형태 관계

대지 100m
: 인접 건축물의 상세 속성, 대지 각 변과의 관계

미시 0~30m
: 인접 건축물 전체 상세정보, 1층·입면·경계·현장사진·관찰
```

먼 거리 건축물에 미시 수준의 상세 API를 호출하지 않는다. 반대로 인접 건축물의 정보를 거시 통계로 뭉개지 않는다.

## 7. QGIS 연계 원칙

QGIS에서 여러 SHP를 무조건 하나의 레이어로 병합하지 않는다.

```text
출처별 원본 레이어 보존
→ GeoPackage 안에서 레이어별 관리
→ 건축물 ID·PNU·주소로 결합
→ 공간 조인은 predicate·겹침비율·신뢰도 기록
→ building_master 생성
→ 범위별 파생 분석 레이어 생성
```

가능하면 다음을 사용한다.

```text
GeoPackage
공간 인덱스
Join attributes by field value
Join attributes by location
Join attributes by location (summary)
Virtual Layer·DB Manager SQL
Processing Modeler 또는 재실행 가능한 처리 모델
```

단순한 시각적 겹침은 동일 건축물 확정이 아니다. 결합 방식과 결합 신뢰도를 기록한다.

## 8. AI 사용 원칙

AI는 원자료에서 모든 계산을 대신하지 않는다.

```text
프로그램
: 개수·면적·거리·교차·분포·매칭률 계산

AI
: 관계의 의미 해석·이슈·키워드·설계 질문·복수 가설 생성
```

분야별 AI를 먼저 실행하고, 전체 분야 종합은 모든 분야 분석이 끝난 뒤 실행한다.

AI 입력에는 다음을 포함한다.

```text
근거 ID
출처
데이터셋
기준일
공간 범위
공간 단위
정규화된 값
계산값
현장 관찰
데이터 공백
```

AI 출력의 모든 FACT와 숫자는 근거 ID를 가져야 한다. 근거가 없으면 `UNKNOWN` 또는 `현장 검증 필요`로 표시한다.

## 9. 건축적 결과 기준

분야별 분석은 단순 요약으로 끝내지 않는다.

최소 출력 항목:

```text
확인된 사실 5개 이상
관계 5개 이상
자료 공백·충돌
핵심 이슈 3개 이상
핵심 키워드
현장 검증 질문
설계 질문 3개 이상
서로 다른 설계 가설 3개 이상
각 가설의 공간적 행동·장점·위험
```

다음과 같은 추상어만 반복되면 분석 실패로 본다.

```text
연결
소통
활성화
지속가능성
열린 공간
```

이 단어를 사용하려면 반드시 특정 건축물·수치·공간관계·현장관찰과 연결한다.

## 10. 사실과 해석 구분

```text
FACT
: API·공식 자료·계산으로 확인한 사실

OBSERVATION
: 사용자가 현장에서 기록한 사실

RELATION
: 두 개 이상의 사실 또는 관찰 사이의 계산·공간·시간 관계

INTERPRETATION
: 관계를 건축적으로 읽은 해석

HYPOTHESIS
: 검증 가능한 공간적 설계 가설

UNKNOWN
: 자료 부족·API 실패·현장 확인 필요
```

geometry 계산면적을 공부면적으로 쓰지 않는다. footprint 면적을 건폐율로 쓰지 않는다. 층수를 높이로 쓰지 않는다. 등록 시설 수를 실제 이용량으로 쓰지 않는다.

## 11. 완료와 체크 규칙

TODO 항목은 다음 조건을 모두 만족해야 체크한다.

```text
코드 또는 문서 반영
테스트 통과
실제 응답 또는 샘플 데이터 확인
원자료·출처·기준일 보존 확인
실패·빈 응답·미확인 상태 표시 확인
사용자에게 보이는 결과 확인
```

검증이 실패하면 기존 항목을 완료 처리하지 않고 다음처럼 추가한다.

```text
- [ ] fix: ...
- [ ] re-verify: ...
```

## 12. 배포 전 확인

```text
pnpm check
pnpm test
pnpm build:pages
```

이후 다음을 확인한다.

```text
GitHub 대상 저장소·브랜치
커밋 파일
GitHub Actions 결과
Pages 상태
배포된 번들 핵심 marker
실제 화면의 데이터·다운로드·출처 표시
```

## 13. 현재 시작 지점

현재 첫 번째 개발 분야는 `주변 건축물 조사`다.

첫 구현을 시작하기 전에 다음 세부 TODO를 별도로 작성한다.

```text
B-01 현재 건축물 자료·QGIS 자료원 감사
B-02 건축물 ID·속성 결합 정책
B-03 거시·중간·대지·미시 데이터 정책
```

이 세부 계획을 확인한 뒤에만 코드 구현을 시작한다.
